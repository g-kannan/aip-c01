01 / What to evaluate

Four questions about an answer.

RELEVANT

On topic?

Does it address the question that was asked?

ACCURATE

True?

Is it correct and grounded in the source?

CONSISTENT

Repeatable?

Same input, similar output, same format.

FLUENT

Readable?

Clear, in the right tone and language.

Add safety as a fifth: harmful, biased or leaking output is a failure whatever the score.

02 / Three scorers

Use the cheapest scorer that can decide.

ScorerGood atWeak at
Deterministic checksFormat, required text, length, forbidden strings, schemaMeaning and quality
LLM as judgeRelevance, coherence, faithfulness, a custom rubricCosts tokens; has its own bias
Human reviewNuance, edge cases, calibrating the judgeSlow and expensive
Start with code. Add a judge for what code cannot see. Sample humans to check the judge.

A custom judge metric needs a prompt, a rating scale and an output schema. For fairness comparisons use a fixed rubric and dataset so two releases are comparable. Bedrock Evaluations offers model evaluation and RAG evaluation jobs, including LLM-as-judge.

03 / Evaluate RAG

Score retrieval and generation separately.

1 / RETRIEVAL

Did it find the evidence?

Recall at k, exact-ID recall, relevance and coverage of the chunks.

→

2 / GENERATION

Did it use it well?

Faithfulness, correctness, completeness of the answer.

→

3 / CITATIONS

Can I verify it?

Do the cited passages support the claims they are attached to?

If retrieval fails, fix retrieval first. A better prompt cannot invent missing evidence.

Bedrock RAG evaluation can assess retrieval only, or retrieval plus generation. Separate scores tell you which half to fix. Use the Retrieve API to inspect chunks directly.

04 / Compare releases

Shadow, canary, ramp.

1 / SHADOW

Run in parallel

Send real traffic to the new version; users see only the old answer.

→

2 / CANARY

A small share

Route a few percent to the new version and watch guardrails, errors, feedback.

→

3 / RAMP

Promote or roll back

Increase in steps; roll back automatically on a breach.

Tag every answer with its prompt and model version so feedback can be split by release.

05 / Release gate

Block the release when a gate fails.

GateExample thresholdAction on breach
Pass rate on the golden setAt least 90 percent, no drop vs baselineFail the pipeline
Safety casesZero failuresFail the pipeline
p95 latencyUnder your SLAFail or warn
Cost per requestAt most 50 percent increaseWarn and review
Synthetic journeysAll pass in stagingFail the pipeline
The gate runs in CI/CD. A human override is logged, not silent.

2

Check the index

08 / Prompts

Change one thing at a time.

Method

  • Fix a dataset of cases
  • Change one variable: wording, example, model, temperature
  • Compare against the baseline
  • Keep the version that wins; log why

Keep it stable

  • Version templates; link answers to the version
  • Validate output against a schema
  • Log prompt version and trace ID
  • Re-run the golden set after every change
