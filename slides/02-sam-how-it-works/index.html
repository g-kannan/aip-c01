Frame the talk: SAM is a thin layer over CloudFormation. The gateway/template.yaml in this repository is the running example on every slide, so each idea can be checked against a real file.

01 / The idea

SAM is CloudFormation with shortcuts.

TEMPLATE

Shorter syntax

One Transform line unlocks AWS::Serverless::* types that expand into full CloudFormation.

CLI

Packaging commands

validate, build, deploy, sync, local and delete package your code and drive CloudFormation.

RESULT

A normal stack

Nothing runs on SAM. You get an ordinary stack: events, change sets, rollbacks, outputs.

In this repo, gateway/template.yaml has 2 serverless resources and 3 plain CloudFormation ones.

How AWS SAM works

02 / 09

SAM has two halves: a template specification, which is a superset of CloudFormation, and a command line tool. The Transform line at the top of the template is what switches the shortcuts on. In gateway/template.yaml the serverless types are ExplainFunction and GatewayApi; the DynamoDB table and the two log groups are plain CloudFormation and are used exactly as they would be without SAM.

02 / What it expands to

Two shortcuts become many resources.

You writeCloudFormation creates
ExplainFunction · Serverless::FunctionA Lambda function, an execution role built from your Policies, and a permission that lets API Gateway invoke it.
GatewayApi · Serverless::HttpApiAn HTTP API with the prod stage, IAM authorizer, route to the function, CORS, access logs and throttling.
Table and log groups · plain resourcesPassed through unchanged. SAM only rewrites the Serverless types.

How AWS SAM works

03 / 09

The expansion happens inside CloudFormation, when the Transform runs during deployment, so the template on disk stays short. To read the expanded result, open the stack in the CloudFormation console, choose the Template tab and view the processed template. The exact list of generated resources can vary with the properties you set, so treat this table as typical rather than exhaustive.

How AWS SAM works

04 / 09

Walk left to right. Steps one and two are local and safe to repeat. Step three is where CloudFormation takes over, and the last card is the result: a stack whose resources and outputs you can inspect. This repository’s README runs unit tests first, then validate, build and deploy, in that order.

04 / sam build

sam build prepares code, not infrastructure.

  • Copies each function’s CodeUri to its own folder.
  • Installs requirements.txt, here boto3.
  • Writes a build template pointing at those folders.
  • You then deploy from that build template.

$ sam build -t gateway/template.yaml

How AWS SAM works

05 / 09

Build does not touch AWS. It turns the source folder into something deployable: one folder per function, with dependencies installed beside the handler. The build template it writes is a copy of your template whose CodeUri values point at those folders, which is why this repository’s README deploys with .aws-sam/build/template.yaml. The folder is generated output and is git-ignored.

05 / sam deploy

Deploy hands the work to CloudFormation.

  1. Zip each function and upload it to S3 (resolve_s3 = true gives you a managed bucket).
  2. Rewrite CodeUri to the S3 location and submit the template to CloudFormation.
  3. CloudFormation runs the Serverless transform and prepares a change set.
  4. You review the change set (confirm_changeset = true); IAM changes require CAPABILITY_IAM.
  5. Resources are created in dependency order, then the stack Outputs appear.
If a first create fails, the stack ends in ROLLBACK_COMPLETE and must be deleted before you retry.

How AWS SAM works

06 / 09

Deploy is the only step that changes AWS. The artifact bucket is managed by the SAM CLI when resolve_s3 is on. The change set is your chance to see what will be created, replaced or deleted before anything happens. CAPABILITY_IAM acknowledges that the stack creates an IAM role, which this template does for the Lambda function. After a successful run, read the Outputs: ExplainUrl and InvokeArn are the values this project copies into .env.

How AWS SAM works

07 / 09

The template declares four parameters: ModelId, ModelResourceArns, AllowedOrigin and HistoryRetentionDays. The first three have no useful default, so sam deploy --guided asks for them and stores the answers in samconfig.toml. HistoryRetentionDays has a default of 1 day in the template, which applies unless you override it on the command line or in samconfig.toml. A value given on the command line beats the config file, and the config file beats the template default.

How AWS SAM works

08 / 09

The two green boxes are the Serverless types SAM expands. Bedrock is called by the function with an IAM policy scoped to the exact model ARNs you pass in, and the history table is plain CloudFormation with a TTL on expiresAt. Two CloudWatch log groups, not drawn, keep logs for 14 days. The stack Outputs are the bridge back to the Streamlit app: ExplainUrl becomes GATEWAY_URL and InvokeArn becomes GATEWAY_INVOKE_ARN.

08 / Operate

Change it, run it, tear it down.

ITERATE

Build and deploy

sam build && sam deploy

Each deploy creates a change set that previews every change.

FAST LOOP

Sync and local

sam sync --watch

Pushes code straight to a dev stack. sam local needs Docker.

TEAR DOWN

Delete the stack

sam delete

Removes the stack. Retained resources, like the history table, stay.

SAM adds no runtime. Everything it makes is CloudFormation, so IAM, drift and rollbacks work as usual.

How AWS SAM works

09 / 09

Close on the idea from the first slide. For day-to-day work, build and deploy again and read the change set. sam sync with watch is a development shortcut that pushes code changes directly instead of going through a full CloudFormation update, so keep it to dev stacks. sam delete removes the stack, but the DynamoDB history table has a Retain policy, so it survives and must be deleted separately when its contents are no longer needed.
