01 / Where controls go

Four places to put a control.

1 / INPUT

Check the input

Length, PII, injection heuristics, topic rules. Block before inference.

→

2 / PROMPT

Shape the prompt

Delimit untrusted text, state rules, grant tools least privilege.

→

3 / MODEL

Guardrail on the call

Content, topic, PII, grounding and prompt-attack policies.

→

4 / OUTPUT

Validate the output

Schema, required text, allowed values. Fail to human review.

Cheapest first: a request blocked at step 1 never costs a model call.

Read left to right. Step 1 is plain code and costs nothing. Step 2 is design: the prompt and the tool permissions limit what a successful injection can do. Step 3 is the managed guardrail. Step 4 is deterministic validation of what comes back. Each layer catches something the others miss.

Six policy types.

Automated Reasoning checks are a separate, newer policy for validating answers against formal rules. The prompt attack filter only makes sense on the input, so its output strength must be NONE. Contextual grounding needs the source passage and the query passed with qualifiers, which is why RAG pipelines are its natural home. Verify the current list in the console: Bedrock adds policy types over time.

03 / Two ways to apply it

On the model call, or on its own.

ATTACHED

Converse / InvokeModel

Pass the guardrail ID and version with the request. Input and output are both checked.

STANDALONE

ApplyGuardrail

Check any text with no model call: another provider, a database row, an upload. Source is INPUT or OUTPUT.

STREAMING

Sync or async

ConverseStream can buffer chunks for checking (sync, safer) or check in parallel (async, lower latency).

ApplyGuardrail is also the cheapest way to test a guardrail against samples.

04 / 09

Converse takes guardrailConfig with guardrailIdentifier, guardrailVersion and optional trace. InvokeModel takes the identifier and version as parameters. For streaming responses the guardrail can run synchronously, which delays chunks until they are checked, or asynchronously, which is faster but may show text before it is flagged. ApplyGuardrail decouples the check from the model.

04 / Roll out safely

Detect first, enforce later.

1 / DETECT

Action NONE

Each policy reports what it would do, and changes nothing.

→

2 / MEASURE

Read the assessments

Count false positives on real traffic, tune thresholds and topics.

→

3 / ENFORCE

BLOCK or ANONYMIZE

Switch the action once the false-positive rate is acceptable.

Create a new version when you change the policy; production keeps calling the old one until you update it.

05 / 09

This is the shadow-test pattern from the practice questions. Detect mode keeps the response unchanged but returns the assessment, so you can see intervention counts without hurting users. Guardrail versions are immutable snapshots of the working draft.

05 / Reduce hallucination

Ground it, check it, cite it.

GROUND

Retrieve first

Answer from retrieved passages, not from memory. See the Knowledge Base Lab.

CHECK

Grounding filter

Score the answer against the source and the question. Below the threshold, intervene.

CITE

Show the source

Return citations so a person can verify each claim.

A relevance score is not proof that the text is true. Keep a human or rule in the loop for high-stakes facts.

06 / 09

Grounding reduces but does not eliminate hallucination. Contextual grounding scores are statistical. Citations let reviewers verify. For regulated claims, add deterministic checks such as numbers that must appear in the source.

This is the practice-question pattern where auto-send is allowed only for valid JSON, grounded numbers and a disclaimer. A guardrail cannot promise a JSON shape. Code can. Use both.

07 / Prompt injection

Assume it will happen.

Two entry points

  • Direct: the user types the attack
  • Indirect: hidden in a retrieved document, web page or tool result
  • Indirect is harder: your own data becomes the attacker

Layers that help

  • Delimit untrusted text; tell the model it is data
  • Tag user input (guardContent) so the prompt-attack filter checks it
  • Give tools least privilege and require approval for risky actions
  • Validate output; red-team before each release

08 / 09

No prompt wording makes injection impossible. The strongest control is limiting what a hijacked model can do: narrow tool permissions, no secrets in the prompt, human approval for irreversible actions. Pre-release red-team suites replay known attacks against staging.
