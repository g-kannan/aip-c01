The Lens says teams that right-size model selection to task complexity and optimize token consumption per invocation can reduce cost without sacrificing decision quality. The common issues are: every call defaults to the most capable model, system prompts and tool catalogs grow unreviewed, caching is treated as one-time setup, customization is pursued on low-volume work where training never pays back, and cost is tracked only in aggregate.

Cascading means the lower-tier model returns a self-assessed confidence and the request escalates only below the configured threshold. Fallback chains per task category move up a tier on timeout or failure instead of retrying the same model. Review routing policies quarterly using AWS Cost Explorer and CloudWatch dashboards, and adjust tiers when thresholds look mis-tuned. Specialized models can be both more accurate and cheaper than general-purpose ones for domain tasks, so include them in the benchmark.

BP02 / Prompt engineering

Every prompt token is paid on every call.

SUGGESTED CONTEXT SPLIT

System prompt20 to 30%
User context30 to 40%
Few-shot examples10 to 20%
Agent scratchpad20 to 30%
  • Replace verbose instructions with structured directives.
  • Go zero-shot first. Add two or three examples chosen by semantic similarity.
  • State the output format and maximum length, and set a hard token cap.
Compression is a fixed-cost cut: it compounds across every invocation.

Audit prompts with AgentCore Observability to measure token footprints, then tighten role definitions and remove redundancy. The context split is the suggested allocation from the Lens, not a rule: system prompt 20 to 30 percent, user context 30 to 40, few-shot examples 10 to 20, agent scratchpad 20 to 30. BP03 / Caching

Cache at three layers.

PROMPT CACHE

Stable prefix

Bedrock prompt caching for system prompts and tool descriptions. Dynamic content breaks the prefix, so move it out.

SEMANTIC CACHE

Equivalent requests

Embed the request, search OpenSearch Serverless, and reuse the answer above a similarity threshold such as cosine 0.95.

PLAN TEMPLATES

Recurring plans

Key plans by task type and parameter signature, then fill in current parameters instead of re-planning.

Each layer fails differently: broken prefixes, weak thresholds, one-size TTLs.

Prompt caching is the highest-impact layer for large stable system prompts; turn it on for agents whose system prompts exceed about 1,000 tokens. A higher similarity threshold reduces false positives but also reduces hit rate, so set it per task type. Plan template examples from the Lens are an onboarding checklist, a support triage decomposition and a reporting workflow plan.

AGENTCOST02 · Model invocation and token cost

10 / 15

Prompt caching keeps the model in the loop: the cached prefix (system prompt, tool definitions, long documents, earlier turns) is read instead of reprocessed, so you save input-token cost and time to first token, but every answer is generated fresh. It needs an exact prefix match, so keep stable content first and variable content last, and the cache expires after a short period of no use. Semantic caching is an application layer you build: embed the question, search a vector store, and above the similarity threshold return the stored answer with no model call. It saves the whole call, but a false match returns a wrong or stale answer, so set the threshold per task type, include the user or tenant in the key for permissioned answers, and invalidate on source changes. Combine them: semantic cache in front, prompt caching on the model call behind it. Exam cues: repeated long context points to prompt caching; similar questions from many users, avoid invoking the model, points to semantic caching; identical requests need only a plain key-value cache. Verify current Bedrock cache TTLs and per-model minimum checkpoint sizes in the documentation.

BP03 / Keep it honest

Caches need invalidation and alarms.

  • Purge entries on events when source data changes, so aggressive caching is safe for moderately volatile data.
  • Set a TTL per task type, so time-sensitive data is not served stale.
  • Accept quantized embeddings only if task success drops less than 2%.
  • Alarm on hit rate per layer in CloudWatch.

ANTI-PATTERNS

Identical prompts at full input price.

Exact-match lookups that miss rephrased requests.

One TTL for every task.

Start with the break-even analysis. The Lens example says monthly inference cost above 500 dollars and volume above 10,000 invocations a month typically reaches break-even within 6 to 12 months. The worked example in the formula is a 5,000 dollar training run saving 400 dollars a month: 5,000 divided by 400 is 12.5, so it breaks even at month 13, ignoring refresh cost. Customization pays off when volume and task stability are both high, and it does not pay off on low-volume categories.

01

Curate

→

02

Quarterly retrain. A/B validation is the promotion gate.

Training data comes from filtered production logs of high-confidence, successful completions, with a sample reviewed manually; the Lens warns against fine-tuning on synthetic data that misrepresents production. QLoRA quantizes base weights to four bits and trains only adapters, which makes single-GPU fine-tuning practical. Options named are Amazon Bedrock model customization jobs, Amazon SageMaker AI Training Jobs with QLoRA, and Amazon Bedrock Custom Model Import. Customization is a pipeline, not a one-off project: schedule quarterly refreshes and gate promotion on A/B validation so drift does not compound silently.

Watch for these

Anti-patterns across the four.

BP01

One big model

Largest model for every task. Hard-coded assignments. No per-tier cost view.

BP02

Bloated prompts

Long personas. Every tool on every call. Unbounded output. Unversioned prompts.

BP03

Naive caching

Full-price repeats. Exact-match only. A single TTL for all tasks.

BP04

Premature training

Synthetic data. Low-volume tasks. One-off projects. Traffic moved without A/B tests.

Aggregate-only cost tracking hides these. Break costs down by model tier.
